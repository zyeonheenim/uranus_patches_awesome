# 群像舞台 · 记忆输出白皮书 v2

> 2026-11-23 定稿。替代 v1（"每人限知 POV 扇出"）。
> 本文为脱敏技术说明，角色名与剧情 id 均为示例占位。
> 一句话：**一场戏一天一份全知总结，原样写进在场每个角色的记忆库；没在场的角色一个字都不写。**

---

## 0. 为什么要改

v1 的逻辑是"每个在场角色各生成一条只写他看得见的部分的 POV"。这套在"角色中途进出"的场景下是对的，但群像舞台的真实用法是：**凡是被勾进本场的角色，从头到尾都在同一个场景里，全场细节共享**。于是 v1 带来三个实际问题：

1. **同一场戏被拆成 N 个版本**：角色 A 那条 4450 字、角色 B 那条 1037 字（其实是上一场戏的）、后面的人干脆没写。同一件事，几个角色记得不一样，日后对不上。
2. **幂等按日期算，不按剧情算**：`povDone` 只看"这一天库里有没有 `pov:` 条目"。结果某场戏当天写好的材料，被**另一场戏**先写下的 POV 误判成"已收"，整段跳过——这一天的记忆从来没进过该场的在场者库。
3. **单人失败无人补**：扇出是逐人串行生成，角色 B 那轮模型超时，收工就报"2 处失败"，但角色 A 那份好好的，没有"用同一份补写"的路子。

v2 把这三件事一起解决：**同一份文本、按剧情指纹幂等、一批写入**。

---

## 1. 核心模型

```
           ┌──────────────────────────────┐
           │  线下剧情存档（一场戏）        │
           │  turns / summaries / castRoleIds │
           └──────────────┬───────────────┘
                          │ 按自然日切分（Asia/Seoul）
             ┌────────────┴────────────┐
             ▼                         ▼
      ┌─────────────┐           ┌─────────────┐
      │ 22 号材料    │           │ 23 号材料    │
      │ small 优先   │           │ small 优先   │
      └──────┬──────┘           └──────┬──────┘
             │ 生成一次                 │ 生成一次
             ▼                         ▼
      ┌─────────────┐           ┌─────────────┐
      │ 全知总结     │           │ 全知总结     │
      │ 第三人称中性 │           │ 第三人称中性 │
      └──────┬──────┘           └──────┬──────┘
             │ 原样复制                 │ 原样复制
       ┌─────┴─────┐              ┌─────┴─────┐
       ▼           ▼              ▼           ▼
   角色A库      角色B库         角色A库      角色B库
   (22号)      (22号)          (23号)      (23号)
   ✗ 未出场者：角色C / 角色D —— 一个字都不写
```

**关键：生成只有一次，写入有 N 次。** N = 本场 `castRoleIds` 里的人数。

---

## 2. 五条硬规则

| # | 规则 | 说明 |
|---|---|---|
| 1 | **按自然日分割** | 用每条 small 的 `from` turn 的 `ts` 折算 Asia/Seoul 日期归桶；同一天多场戏合并，带【剧情名】头。跨天的戏自然切成多份。 |
| 2 | **small 优先** | 一天里只要有 small 就用 small 拼接；只有 big 的日子才退用 big。与 `endOffline` 同一口径。 |
| 3 | **全知第三人称中性版** | 每天只生成一份，写"这一天从头到尾发生了什么"。所有在场角色全程在场、全场细节都知道——**不再写"他只看见/只听见"的限知句**，不再分视角。人名一律本名，叙述里不出现"我"。 |
| 4 | **原样注入** | 同一份文本，字节级相同，写进每个在场角色各自的记忆库。谁在场谁拿一份，不在场的跳过。 |
| 5 | **幂等按剧情指纹** | 指纹 = `cast:<首剧情id>-<日期>.md-<材料字数>`，落在每条记忆的 `keywords`。**只认本剧情本日期本长度的指纹**；同日期别的剧情写的条目不算数。 |

## 3. 数据长什么样

一条 v2 记忆（写在角色 A 库，举例）：

```json
{
  "id": "m-xxxxxxxx-x",
  "date": "2026-11-23",
  "timestamp": 1795415129419,
  "content": "2026年11月23日 00:30，某公寓主卧。……（全知第三人称正文）",
  "keywords": [
    "群像", "角色A", "cast",
    "cast:<剧情id>-2026-11-23.md-<字数>",
    "2026-11-23"
  ],
  "embedding": null
}
```

同一天角色 B 库那条：`content` **逐字相同**，只有 `keywords[1]` 换成"角色B"。未出场角色的库里没有这条。

> 兼容：v1 的 `pov:` 指纹条目不删除、不改写，v2 只按 `cast:` 指纹判重。旧条目留在库里当历史，只是不再作为幂等依据——这正是 22 号误判的根治点。

## 4. 收工流程（点"结束"后发生什么）

1. `endOffline` 落库完毕 → spawn 收工脚本（detached 后台，带并发锁）。
2. 收工脚本读本场 `castRoleIds`，反查在场角色姓名（无字段的老戏兜底全员都在）。
3. 读所有 `summaries`，按 small 的 `from` turn 日期归桶；每天拼成一份材料。
4. 对每一天：
   - 算指纹 `cast:<首剧情id>-<日期>-<字数>`；
   - 若**所有在场角色库**都有这个 `cast:` 指纹 → 跳过；否则继续；
   - 把材料写到 `/tmp/uranus-closeout/<首剧情id>-<日期>.md`；
   - 调扇出脚本 `--file <材料> --date <日期> --present <在场> --run --shared`。
5. 扇出脚本生成**一份**全知总结，循环写入每个在场角色库；逐人写、逐人记成功失败。
6. 结果回报控制台日志抽屉（`scope=群像收工`）。

**与 v1 的差别**：第 4 步的判重从"日期 + 任意 `pov:`"改成"剧情 + 日期 + 字数 + 本场全部在场者"；第 5 步从"每人各生成一次"改成"生成一次、写 N 次"。

---

## 5. 失败与重跑

- **模型失败**：连吃 3 次空回/异常就记日志，不为这天烧更多钱；其他天照跑。
- **向量失败**：`sandbox` 出口漂移导致 Google embed 全域 400 时，条目照样写，标 `无向量`。语义检索会漏这条，但关键词/日期检索仍在。
- **写一半失败**：重跑即可。`cast:` 指纹逐人去重——已写的跳过，缺的补上，不会写重。
- **想强制重写某一天**：手动删掉那几个库里带目标 `cast:` 指纹的条目，再跑。

---

## 6. 玩家侧可见变化

- 收工日志里的"各人 POV"改名"在场者共享记忆"，日志写清写了哪几个库、每库多少字。
- 群像库的大总结保留（这是给群像舞台卡自己回看的集体档），但**角色记忆以共享版为准**。
- 白皮书（玩家版）对应段落同步改写："原样注入在场每个角色的记忆库，未出场角色不会知道这场戏"。

---

## 7. 已知边界

- **中途进出的角色**：v2 假设勾进本场 = 全程在场。若某角色第 30 轮才进场，他也会拿到全天的共享版——这是 C 方案的明确取舍（群像默认全场细节共享）。
- **不同场的同日**：多场戏同一天会合并成同一份材料（`【剧情名】` 分隔），写进各自在场者的库。
- **老剧情**：没有 `castRoleIds` 的老戏仍按全员在处理，产出 `cast:` 新格式记忆；不会动它们已有的 `pov:` 老条目。
